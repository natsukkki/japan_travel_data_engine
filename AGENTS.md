# Ориентиры для агента

## Назначение и способ работы

Это учебный портфолио-проект по Data Engineering. Пользователь хочет понимать решения и самостоятельно писать рабочий код. При обсуждении, диагностике и ревью сначала объясняй фактическое поведение и помогай найти следующий шаг; не переписывай рабочий код без прямой просьбы. Полную реализацию рабочего кода делай по прямому запросу, поясняя причины выбора, альтернативы и ограничения. Тесты пиши и поддерживай самостоятельно; если тест обнаружил ошибку в коде пользователя, объясни её до изменения рабочего кода.

При архитектурном выборе соотноси сложность с масштабом pet-проекта. Отделяй реализованное от плана, факты кода от рекомендаций. Не называй будущие сервисы работающими. Значимые изменения архитектуры сначала обсуждай с пользователем. Более подробные пользовательские предпочтения лежат в `../docs/пользовательские инструкции.txt` (это соседняя папка вне репозитория); если файл доступен, учитывай его.

## Стиль нового кода и примеров в чате

- Перед предложением кода сверяй оформление и структуру с существующими модулями той же части проекта.
- Пиши docstring на английском; сообщения об ошибках и логи — на русском, как в существующем коде.
- Сохраняй понятные имена в `snake_case`, аннотации типов, константы уровня модуля и передачу настроек через `Settings` / `SparkSettings`.
- Разделяй этапы на небольшие функции; общий порядок выполнения собирай в `run_*()`, точку входа — в `main()`.
- Замечания о плохих практиках объясняй при работе над новым или текущим незавершённым кодом. Не устраивай ретроспективное ревью и не переписывай уже запушенный код ради единообразия без прямой просьбы пользователя. Отделяй ошибки и риски от вкусовых предпочтений.

## Где что находится

- Проектная документация хранится в существующей соседней папке `../docs/`, на одном уровне с репозиторием. Новые заметки сохраняй туда; не создавай вторую папку `docs/` внутри репозитория.
- `README.md` — текущий статус, схема будущей системы и локальный запуск.
- `ingestion/batch/` — четыре загрузчика: Open-Meteo, JTA tourism, e-Stat regional price index, JMA sakura.
- `storage/minio.py` — общие операции записи и чтения MinIO для ingestion и processing. Фабрика клиента принимает endpoint и ключи доступа явно, без зависимости от классов настроек загрузчиков.
- `ingestion/batch/config/regions.json` — восемь выбранных регионов, координаты и числовые `prefecture_code` для сопоставления с JTA.
- `processing/spark/load_regions.py` — загрузка справочника в PostgreSQL.
- `processing/spark/jta_excel_parser.py` — разбор JTA Excel и отбор префектур по `regions.json`; проверяет все 47 префектур источника, возвращает только выбранные (8 строк за месяц, 96 за полный год). При чтении справочника строит словарь `prefecture_code → region_code`, добавляет `region_code` в результат; японское название префектуры в результат не включается.
- `processing/spark/weather_etl.py` — ETL ежедневной погоды в DDS.
- `processing/spark/tourism_etl.py` — ETL месячной статистики JTA: читает текущие версии из state, присоединяет `region_id`, загружает staging и обновляет DDS с учётом приоритета публикаций.
- `processing/spark/jdbc.py`, `config.py`, `session.py` — доступ к PostgreSQL и настройка Spark.
- `infrastructure/config/postgres/init/` — создаваемые при первом запуске volume схемы и таблицы.
- `infrastructure/docker/docker-compose.yml` — сейчас MinIO, PostgreSQL и Spark.
- `../docs/weather-ingestion-recovery.md` — точные правила повтора погодной загрузки.
- `tests/` — unit-тесты и тесты Spark без записи в реальные MinIO и PostgreSQL.
- `../docs/архитектура-проекта.md` — отдельное описание архитектурных решений вне репозитория, если соседняя папка доступна.

## Инварианты и ограничения

- Сверяй описание с кодом: `dds_schema` и **`marts_schema`** создаются SQL-скриптом; dbt и витрины пока только запланированы.
- Batch raw-файлы хранятся в MinIO. Kafka, Airflow, dbt, Spark Structured Streaming и Streamlit пока не реализованы.
- Реализованы ETL погоды и туризма; ETL индекса цен и сакуры ещё не написаны. Spark запускается локально через `local[2]`; кластер и переход на Iceberg отложены до завершения текущего проекта.
- Погодный ingestion хранит state по регионам в `state/openmeteo_weather.json`. Сначала пишет и проверяет raw-объект, затем подтверждает прогресс в state. Ключ нового файла зависит от региона и начальной даты диапазона; повтор может заменить содержимое того же ключа.
- Spark ETL выбирает погодные ключи, которых нет в `dds_weather_processed_files`. После проверок пишет staging, затем переносит строки в `dds_weather_daily`, регистрирует ключи и очищает staging в одной транзакции PostgreSQL. JDBC-запись staging не входит в эту транзакцию.
- Зерно погоды в DDS — `(region_id, weather_date)`; дубли дат и неизвестные регионы отклоняются. Автоматическое исправление ранее обработанного raw-объекта не реализовано.
- Туристический ingestion сохраняет Excel по ключам с SHA-256 и обновляет `state/tourism_statistics.json`. Логические ключи — `final:YYYY` и `second_preliminary:YYYY-MM`; state указывает текущую версию каждой публикации, а старые объекты остаются в raw.
- Туристический ETL читает только объекты из state. `dds_tourism_processed_files` имеет первичный ключ `logical_key` и хранит последнюю успешно обработанную версию `object_key` с `processed_at`, а не всю историю файлов. Сравнение текущих `object_key` с этой таблицей поддерживает повтор и смену версий A → B → A; ingestion для этого менять не нужно.
- `logical_key` добавляется к результатам парсера в ETL, включается в схему DataFrame и сохраняется при присоединении регионов и записи staging. В `dds_tourism_monthly` это поле не записывается.
- Зерно туризма в DDS — `(region_id, year, month)`. `final` имеет приоритет над `second_preliminary`; тот же тип публикации обновляет изменившиеся показатели. Сначала SQL выбирает одну публикацию на зерно через `DISTINCT ON`, затем выполняет upsert. Даже месячная публикация, не изменившая финальные показатели DDS, регистрируется как обработанная.
- Перед JDBC-записью туристический ETL очищает staging и после записи сверяет количество строк. Upsert DDS, upsert обработанных публикаций по `logical_key` и очистка staging выполняются одной транзакцией; JDBC-запись staging в неё не входит. `tourism_rows` — число входных строк staging до выбора публикаций, а не число вставленных или обновлённых строк DDS.
- JTA Excel разбирается через SDK MinIO и `openpyxl` в памяти Python-драйвера, затем создаётся Spark DataFrame. Не описывай чтение Excel как распределённое; текущий объём данных небольшой.
- В текущем дизайне одновременно выполняется один запуск каждого пайплайна. Перед ETL соответствующий ingestion должен успешно завершиться.
- SQL из `postgres/init/` исполняется только при первом создании PostgreSQL volume. Существующую схему обновляй адресно; не удаляй volume ради миграции.
- Для туризма нужны SQL-скрипты `06`–`08`. Если таблицы уже созданы без `logical_key`, изменение init-скриптов не обновит их: требуется отдельная миграция. Готового скрипта миграции пока нет.
- Туристический ETL проверен на 10 реальных JTA Excel (256 строк) через настоящий Spark JDBC во временную PostgreSQL 18, с локальным HTTP-сервером вместо MinIO. Проверены повтор и смена версий A → B → A. Не выдавай эту проверку за полный запуск Docker Compose с настоящим MinIO и PostgreSQL 16: такой запуск пока не подтверждён. Сквозная проверка погодного ETL с PostgreSQL также пока не подтверждена.

## Команды проверки

Из корня репозитория в PowerShell:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Для тестов Spark нужны зависимости из `processing/spark/requirements.txt` и Java 17+. На macOS/Linux используй `.venv/bin/python` вместо Windows-пути. Обычный набор тестов работает без внешних источников и записи в MinIO/PostgreSQL; отдельная проверка во временной PostgreSQL в него не входит. Не запускай реальные ingestion или ETL для проверки документационных правок: они обращаются к внешним источникам и меняют MinIO/PostgreSQL.
